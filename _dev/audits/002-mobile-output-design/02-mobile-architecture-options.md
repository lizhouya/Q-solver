# 02 — 移动输出候选方案比较（Mobile Architecture Options）

> 只读设计审计。本节为「把 AI 答案推送到手机浏览器」提供**候选架构比较**。
> ⚠️ **本审计不选型**：A/B/C/D 均给出利弊与适用性，最终选择由用户/产品决策（见 06-user-decisions.md 与最终报告）。

---

## 方案 A — WebSocket（专用长连接）

**形态**：桌面端内起一个 WebSocket Server（如 Go 标准 `net`/第三方 ws 库），手机浏览器 `new WebSocket('ws://192.168.x.x:PORT')` 订阅事件流。

| 维度 | 评价 |
|---|---|
| 实时性 | ⭐⭐⭐⭐⭐ 双向 + 低延迟；流式 chunk 天然逐条推送 |
| 实现成本 | 中。后端需要一个 tiny ws server + 认证 token + 连接生命周期管理 |
| 与现有事件流契合 | ⭐⭐⭐⭐⭐ 当前是事件驱动（`EmitEvent`），可直接把每个 emit 转成 ws 帧 |
| 断线重连 | 浏览器 WebSocket 支持自动重连（需应用层 handle）；服务端需清理陈旧连接 |
| 多设备 | 支持多连接（每连接独立订阅） |
| 坑 | 需处理心跳/超时/连接池；CORS 无关（ws 无跨域限制）；局域网需开放端口 |

**适用性**：流式思考+内容（当前强需求）最自然；与 F-001 多轮（若将来接入历史）也好扩展。

---

## 方案 B — HTTP Polling（轮询）

**形态**：后端暴露 `GET /api/solution/latest` 之类接口，手机定时（如 1~2s）拉取最新状态。

** 维度 | 说明 |
|---|---|
| 实时性 | ⭐⭐ 取决于轮询间隔；chunk 级粒度需高频轮询（浪费） |
| 简单性 | ⭐⭐⭐⭐⭐ 实现最简单，无长连接复杂度 |
| 与流式契合 | ⭐⭐ 适合「最终答案」形态；对「思考链逐字流」体验差 |
| 断线 | 天然无状态，重连=下一次轮询即可 |
| 带宽/功耗 | 高频轮询对手机电量和服务器压力不友好 |

**适用性**：若 Mobile 只展示**最终答案**（不做流式打字机），轮询足够且最省。旧的 Q-Solver 需要流式，若选 B 需砍掉流式愿景或降级展示。

---

## 方案 C — SSE（Server-Sent Events）

**形态**：桌面端起 HTTP 长连接 `text/event-stream`，手机 `EventSource` 订阅；单向（服务端→客户端）推送。

| 维度 | 说明 |
|---|---|
| 实时性 | ⭐⭐⭐⭐⭐ 单向流式推送，天然逐 chunk |
| 实现复杂度 | ⭐⭐⭐⭐ 低（Go `http.ResponseWriter` + `text/event-stream`），无 ws 握手帧 |
| 断线重连 | ⭐⭐⭐⭐⭐ 浏览器 `EventSource` **内置自动重连**（retry 头）、last-event-id 可续传 |
| 双向需求 | ⭐⭐ 若手机端还要「控制桌面」（停止/重新解题）则 SSE 单向不够，需搭配 POST |
| 兼容性 | 现代移动浏览器均支持 EventSource（iOS Safari 13+ 已嫁） |

**适用性**：**单向推送流的完美典型**。与「桌面 → 手机只读展示」高度契合；无需处理 WebSocket 低层协议麻烦；浏览器自带自动重连比 WS 省代码。

---

## 方案 D — 其他既有机制

| 子方案 | 说明 | 可行性 |
|---|---|---|
| D1 复用 Wails 事件 → 局域网网关 | 前端把 Wails 事件转发到公共 HTTP/WS 网关 | 中（放大风险，依赖 WebView 存活，且多一次跨进程） |
| D2 定时写文件 → 手机 SMB/HTTP 拉取 | 桌面把答案写 `userConfigDir/输出/*.md`，手机浏览文件共享 | 低（需要共享盘/局域网文件服务，体验差） |
| D3 远程 (cloud relay) | 桌面 POST 到云中继，手机从云拉 | 高实现成本 + 隐私顾虑（答案含题面/简历），与本地优先冲突 —— 明确不推荐 |
| D4 复制到剪贴板/浏览器打开 | 手机扫二维码直接打开局域网 URL（浏览静态输出） | 可作**辅助连接**（见 15-连接方式），非传输架构本身 |

---

## 比较汇总（供用户决策）

| 维度 | A WebSocket | B Polling | C SSE | D 其他 |
|---|---|---|---|---|
| 流式 UI | 优 | 差 | 优 | 依方案 |
| 实现成本 | 中 | 最低 | 低 | 中 |
| 断线重连 | 需自实现 | 天然 | **内置** | 视方案 |
| 双向控制 | 优 | 差 | 需另补 | — |
| 资源占用 | 低 | 中（轮询） | 最低 | — |
| 与「只读展示」定位契合 | 中 | 中 | **最高** | — |

**结论性观察（非选型）**：若产品定位为「手机只读、看完整流式过程」，**SSE 在浏览器兼容、重连、实现成本三者平衡最好**；若要「手机也可反控桌面」，WebSocket 更妥当。**本审计不替用户拍板**，此观察供 `06-user-decisions.md` 及最终报告参考。
