## 1. 背景与问题

用户反馈当前截图存在偶发阻塞，有时第一张截图后无法继续；原本可连续截取最多 3 张并一起解题，现在实际使用中难以稳定完成；截图后用于展示已截张数及删除、发送等快捷键指引的临时悬浮提示也未按预期出现。

只读核查确认：

- 后端仍保留 `MaxScreenshots = 3`，发送时仍会复制完整截图缓冲并一次性交给 Solver；多图能力没有从协议或 Solver 中删除。
- Windows `WH_KEYBOARD_LL` 回调当前同步执行 `OnTrigger`，截图动作会在 Hook 回调线程内完成屏幕捕获、缩放、锐化、编码和事件发送。耗时回调可能阻塞键盘处理，并可能被 Windows 因超时静默移除 Hook。
- `ScreenshotDock.vue` 仍有张数、删除和发送提示，但快捷键值在组件初始化时一次性读取，没有保持 Pinia 响应性；Change 034 验证记录也明确注明当时稳定版未包含 ScreenshotDock 快捷键显示修复。

## 2. 目标

1. Windows Hook 回调不再同步执行截图、压缩或 Wails 事件等耗时业务操作。
2. 快捷键动作在后台按触发顺序串行执行，保持 `截图 → 截图 → 截图 → 发送` 的确定顺序。
3. 恢复连续截取最多 3 张图片并在一次请求中共同解题的既有行为。
4. 截图成功后稳定显示悬浮 Dock，展示当前张数和实际生效的继续截图、删除、发送快捷键。
5. 不改变模型请求协议、题库结构、用户配置格式或现有快捷键绑定。

## 3. 验收标准

- [x] Windows Hook 命中快捷键后只执行轻量入队，不直接运行截图或其他业务回调。
- [x] 首个动作处理被人为阻塞时，后续动作仍可快速入队，且最终严格按 FIFO 顺序执行。
- [x] 连续触发 3 次截图后缓冲区可包含 3 张图片；第 4 次仍按既有规则拒绝。
- [x] 发送动作在此前截图动作全部完成后执行，一次请求携带 3 张图片且顺序不变。
- [x] 截图 Dock 显示 `1/3` 至 `3/3`，并展示当前实际截图、删除、发送快捷键；设置加载或更新后提示同步刷新。
- [x] 发送开始、删除截图和清空截图后的 Dock 状态与后端状态一致。
- [x] 聚焦测试、`go test ./...`、`go vet ./...`、`go build ./...`、全部前端回归、`npm --prefix frontend run build` 和 `wails build` 如实记录。
- [x] Windows GUI 人工验证项目明确记录为 PASS、FAIL 或 NEEDS_USER，不以自动测试替代。

## 4. 非目标 / 明确不做

- 不改变 `MaxScreenshots = 3`。
- 不自动在第 3 张截图后发送，继续保留显式发送快捷键。
- 不并行执行多个截图动作，避免截图和发送乱序。
- 不修改模型 Provider、Prompt、题库 schema、Mobile SSE 协议或输出路由。
- 不新增第三方依赖，不升级 Go、Wails、Node 或前端依赖。
- 不读取、修改或输出用户 API Key、Token、个人配置和题库内容。

## 5. 影响面预估

- 涉及业务源码文件（预计）：`pkg/shortcut/service.go`、新增 `pkg/shortcut/dispatcher.go` 及测试、`frontend/src/components/ScreenshotDock.vue`、新增前端回归测试。
- 需要同步更新的文档：本 Change 七份档案、`_dev/changes/INDEX.md`，必要时增加提交边界审计。
- 潜在风险：动作队列停止语义不当、快捷键顺序变化、Dock 提示与真实绑定不一致、Wails 构建生成噪音。

## 6. 附带约束

- 严格保持动作 FIFO，不使用每次触发一个无序 goroutine 的实现。
- Hook 回调不得等待截图完成，也不得因业务动作耗时长期阻塞。
- 构建前后检查 `frontend/wailsjs`、`go.mod`、`go.sum` 和 Git 差异，禁止混入生成噪音。
- 本次批准只覆盖本地实现与验证，不包含 commit、push、Tag、Release 或稳定版晋升授权。
