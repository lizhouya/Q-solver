## 1. 背景与问题

当前设置把 API 接入与模型选择拆分在“API”和“模型”两个标签页，用户需要跨页完成接口配置、模型刷新、模型选择和连接验证。CCR 又以独立 `connectionMode` 呈现，虽然底层仍复用 OpenAI Chat adapter，却拥有强制协议、禁用真实 probe 和专属文案，造成概念与实现分叉。

现有“自定义”只允许填写 Base URL 并选择三种已有协议，不支持受约束的 Endpoint Path、额外 Headers 或 `response_format`。API Key 被前端刷新/测试流程强制要求，也阻止无需鉴权的本地兼容服务。

用户要求参考其提供的 API 设置布局，把 CCR 统一规划到自定义接口中；选择模型后同页提供“保存 API 设置”“刷新候选模型”“测试 API 连接”按钮，使 Q-Solver 能以一致方式接入更多兼容接口。用户明确要求先制定计划，再实施。

## 2. 已确认决策

- 采用**结构化通用接口**，不实现任意 JSON 请求/响应模板引擎。
- 保留单一当前生效配置，不实现多接口档案。
- “测试 API 连接”执行一次最小文字真实请求，可能产生少量费用。
- CCR 不再是特殊运行模式，但保留“CCR 本地网关”快捷预设。
- 自定义/本地接口允许 API Key 留空；为空时不发送默认鉴权头。
- API 和模型设置合并为“模型与 API”统一页面。
- Endpoint、Headers、`response_format` 使用受约束配置，不改变强类型协议 body 和流式解析。

## 3. 目标

1. 用一套协议驱动的连接草稿统一官方服务、OpenAI 兼容网关、CCR 和无鉴权本地服务。
2. 将 API 字段、模型选择、保存、刷新和测试放在同一页面完成。
3. 继续复用 OpenAI Chat、OpenAI Responses、Anthropic Messages 三个 adapter，不按模型名、品牌或 URL 猜协议。
4. 旧 CCR 配置无损加载，首次保存后规范化为统一自定义接口配置。
5. 三个操作均使用当前未保存草稿，且保存、刷新、测试之间没有隐式副作用。
6. 保持凭据加密、诊断脱敏、迟到响应隔离和保存失败不替换生效配置。

## 5. Revision A 非目标（历史；其中多连接限制已被 Revision D 取代）

- 不实现多接口档案、命名、切换、删除或密钥分组。
- 不实现任意请求模板、响应字段映射或自定义 SSE 解析。
- 不自动探测协议，不自动 fallback 或重试到其他协议。
- 不管理 CCR 的安装、启动、进程或私有配置。
- 不修改 Solver、题库、Mobile、截图、历史上下文或 Prompt 语义。
- 不新增依赖，不升级 Go、Wails、Vue、Node 或 SDK。
- 不自动调用真实收费接口，不读取或输出用户真实凭据。
