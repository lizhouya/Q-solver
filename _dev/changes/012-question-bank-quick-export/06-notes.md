# 总结与注意事项 06

## 变更摘要

Change 012 已将题库工作流改为“配置一次、自动记录、按当前段一键导出”：

- `ArchiveDir` 直接作为最终题库目录，恢复数据放在 `_记录/`，用户导出不再出现重复层级。
- 首次解题懒创建当前段；导出、手动分段或软清空后，下一题自动进入新段。
- ActionBar 的“导出题库”处理当前段全部提交；历史列表提供显式“重试整理 / 导出”，不会放开普通按钮的重复点击。
- 模型整理默认关闭；开启后按记录逐条提炼 Category、Type、题干、知识点和解题要点，原答案保持原文。
- 手机端展示真实快捷键，并接收由桌面按钮或快捷键按输出模式路由的滚动控制。
- Windows hook 原生参数在 platform 层复制，`go vet ./...` 已通过。
- 对故障审查发现的数据可靠性问题补充了回归测试：首次保存失败、dirty 终态覆盖、导出部分成功、控制队列满和截图大小不一致。
- 已按用户明确要求实际整理仓库外旧输出：3 个 v1 会话迁入 `_记录`，5 份旧导出扁平化到最终题库根，旧空“自动网申”和重复空层级已移除。

## 经验与踩坑

| 现象/坑 | 原因 | 结论/建议 |
|---|---|---|
| 首次懒建段保存失败后 Begin 返回空 ID | Store 在创建空 Session 失败后提前返回 | 只要内存中建立了题目记录，就返回稳定 ID 与错误，让 App 继续关联最终答案并提示重试。 |
| Ended 段保存失败后被下一题覆盖 | `ensureWritableLocked` 只看状态，不看 dirty | 任何非可写终态只要 dirty 就必须阻止建新段。 |
| 部分整理失败后无法重试 | App 一律先 Seal，而 Seal 拒绝 Exported | 区分普通当前段动作与显式历史动作；历史按 ID 直接整理/导出。 |
| SSE channel 满时滚动命令丢失 | 所有快照都使用同一非阻塞发送且 default 丢帧 | 控制帧满队列时替换积压的全量业务快照，普通帧仍可丢弃以保护解题主流程。 |
| 写入接受约 21 MiB 图片，导出只读 20 MiB | 入口只限制 data URL 总长度 | 解码后再次执行 20 MiB 硬限制，使 writer 与 reader 契约一致。 |
| Wails `-skipbindings` 仍改写 runtime shim | 本机 CLI 2.16.0 高于项目模块 2.11.0 | 构建前后比较哈希，精确恢复 runtime 噪音；不运行自动升级或批量恢复。 |
| 首次 Wails 命令传入 `-dir` 失败 | v2.16.0 build 不支持该参数 | 在仓库目录执行命令；失败调用未开始构建且哈希无变化。 |
| 后台审查 agent 多次 429 | API 用量限制 | 主线程基于已返回的状态序列补故障测试并完成修复，不把未完成 agent 报告当作验证。 |
| `go test -race` 启动即 `0xc0000139` | 既有 Windows race 工具链/运行环境问题 | 标记 `BLOCKED`，普通测试通过不能替代 race 结论。 |

## 对本项目后续的影响

- 后续题库功能应继续以“原始记录不可变、结构化结果可重试、导出不覆盖”为边界。
- 新增状态或迁移版本时，需要同时维护 `SnapshotByID`、legacy reader、历史显式动作和前端只读状态。
- Mobile 控制仍是有界队列；极端连续超过 channel 容量的控制输入可被限流，但正常控制不会被业务流式快照挤掉。
- Wails CLI 与项目模块升级应作为独立 Change 处理，不应混入题库功能提交。
- 当前所有修改仍与 Change 010/011 的既有未提交内容共存；后续提交前必须按审计边界精确暂存，不能使用 `git add .` 或 `git add -A`。

## 2026-10-20 Mobile 人工反馈回修补充

- 顶部上下箭头原本就是答案滚动入口；本次将其包装为明确的控制组，并只在鼠标位于该组上时接收 wheel。
- 设置页连接入口消失并不等同于用户选择了错误模式。服务在 App 启动时独立初始化，而 `tempSettings.outputMode` 只是未保存草稿；两者必须分别展示。
- 读取 Wails 状态失败、固定端口不可监听和服务初始化失败不能合并成同一错误，否则用户无法判断应“重新读取”还是“重试服务”。
- Mobile 控制消息虽然沿用完整 Snapshot，但浏览器必须按业务 `seq` 决定是否重渲染；否则一次滚动会重建答案、打断平滑滚动，并把历史答案选择切回最新。
- Server 重试复用同一实例和 Bridge；运行中重试不轮换连接凭据，重试成功也不补偿执行窗口隐藏策略。
- 自动化已覆盖协议和 DOM 状态机，但 Windows WebView2 的触控板手感、真实手机 SSE 重连及三种输出模式仍为 `NEEDS_USER`。
- Change 012 因本次人工反馈继续保持“待人工复验 / 未提交 / 未关闭”；不创建 Change 014。

## 2026-10-22 回修结论

此前“业务 seq 增量渲染”与 Bridge 实际发出的序号不一致，导致后续答案被页面当作重复帧。旧测试手造递增序号，仅验证了浏览器假设，没验证生产者契约；现以真实 Bridge → HTTP/SSE → Node 页面联合测试补足。队列最终帧不能套用“下一帧会补齐”的中间帧丢弃策略。

代码修复及自动验证完成；新交付 build/bin/Q-Solver-sync-fix.exe 含 API 恢复功能，待用户跨电脑复验。未提交、未关闭，未调用真实模型。
