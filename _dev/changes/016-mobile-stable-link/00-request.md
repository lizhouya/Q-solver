## 1. 背景与问题

当前 Mobile 服务每次完整启动都会生成新的随机 Token，因此即使端口固定为 `38511`，同步链接也会变化。已有的 `Bridge.Reset()` 只更新服务端最新快照，无法清除浏览器会话内历史、答案与错误 DOM，也无法阻止清屏前任务的迟到输出重新污染同步端。

固定长期链接后，旧浏览器还会跨进程自动重连，因此还必须解决业务序号从零开始、旧 Token 已连接 SSE 的撤销、服务端清屏重放和旧任务输出隔离问题；不能只把 Token 写入普通设置，也不能只发送一次性清屏控制帧。

## 2. 目标

1. 默认启用固定同步链接；升级后首次启动生成一次新 Token，之后在配置目录、IP 与端口不变时跨完整重启复用。
2. 允许用户关闭固定链接；关闭后立即换链接并清屏，后续每次完整启动生成新的临时 Token，同进程 Retry 不轮换。
3. 重新启用固定链接时生成全新的持久 Token，不恢复关闭前凭据。
4. “重试服务”“清空同步端显示”“重置同步链接”职责分离。
5. Reset 同时轮换 Token、撤销旧 URL 的新请求与既有 SSE，并让新链接从空白显示边界开始。
6. Clear 清除同步页面当前内容和页面会话历史，且刷新、断线重连、旧帧与清屏前任务都不能恢复旧内容。
7. Clear/Reset 不删除桌面答案、题库记录、历史分段、导出文件、截图、普通配置或 Solver 上下文，也不取消正在执行的任务。
8. UI 准确说明：固定的是 Token 与端口，不保证 IP 不变；成功只表示状态已提交并广播，不代表所有远端设备已确认。

## 3. 验收标准

- [ ] 固定模式下，相同网络地址的完整重启继续使用同一 Mobile URL；新进程低业务序号仍被页面接受。
- [ ] 关闭固定模式后当前链接立即轮换并清屏，下一次完整启动再次轮换；同进程 Retry 保持链接。
- [ ] 重新启用固定模式生成新链接，后续完整重启复用，且不恢复关闭前 Token。
- [ ] Reset 后旧 URL 的页面与 SSE 请求返回未授权，旧 SSE 主动断开，新 URL 首帧为空。
- [ ] Clear 后答案、分析、错误、宽窄屏历史和旧滚动回调全部清空，刷新与重连不恢复旧内容。
- [ ] Clear/Reset 前启动任务的迟到 Mobile 输出被抑制；题库、桌面路由、模型上下文与任务完成保持原行为；后续新题正常同步。
- [ ] Mobile Token 不进入普通 Config、Snapshot、日志、Toast、文档、浏览器存储或测试错误输出；状态文件不含明文 Token。
- [ ] 端口占用或 Mobile 状态读取失败不阻断桌面解题；端口恢复后 Retry 使用最新已提交 Token。
- [ ] Go、前端、Mobile DOM、Vite 与 Wails 自动验证如实记录；真机项目未验证时标记 `NEEDS_USER`，race 环境阻塞时标记 `BLOCKED`。

## 4. 非目标 / 明确不做

- 不新增云端中继、HTTPS 证书、账号登录、客户端 ACK 或远程删除能力。
- 不保证局域网 IP、DHCP 租约或网卡切换后完整 URL 永远不变。
- 不把现有应用内固定密钥 AES-GCM 描述为 DPAPI、Keychain 或硬件绑定密钥库。
- 不改 ActionBar、solution store、题库 Store、Solver chat history 或截图清理流程。
- 不新增依赖，不升级 Wails runtime，不调用真实模型。
- 不提交、推送、创建 Tag 或 Release，除非之后获得新的明确授权。

## 5. 影响面预估

- 后端：Mobile 专用状态、Bridge 协议、HTTP/SSE 鉴权、App 生命周期、解题任务代际。
- Mobile 页面：跨进程 session、清屏边界、历史与 DOM 清理、旧 rAF 隔离。
- 桌面前端：共享 Mobile store、设置页管理入口、TopBar 清屏入口、统一确认层。
- 文档：README 中英文、Change 016 全套记录、INDEX。
- 风险：状态写盘与运行态分裂、SSE 撤销竞态、清屏后旧输出复活、长期凭据泄漏、关闭阶段死锁。

## 6. 附带约束

- 分支固定 `dev/qsolver-custom`，不改写既有提交历史。
- Token 只允许存在于后端内存和专用加密状态；完整 URL 只进入受控的 `MobileInfo.URL` 与设置页展示/复制。
- 所有链接或显示边界变更先持久化，再执行无 I/O、无失败的运行态切换。
- 生产端口继续为 `38511`；测试可使用内核分配端口。
- 遵守 `AGENTS.md > CLAUDE.md > 本 Change`。

## 7. 2026-10-23 补充请求：确认层遮挡与 Windows 清屏快捷键

用户在 Change 016 验证版中确认“清空同步端显示”入口可见，但运行状态面板覆盖了根级确认层；同时要求以 `Shift+C` 控制清屏，并把该动作加入“设置 → 常规”的快捷键清单。

补充验收标准：

- [ ] 点击状态面板清屏按钮后，状态面板立即关闭；150ms leave 动画残留也始终位于确认层下方。
- [ ] Windows 新增 action `clear_mobile_display`，默认 `ComboID=67+160`、`KeyName=Shift+C`；该组合严格表示当前 Hook 语义下的左 Shift+C。
- [ ] 快捷键只发起共享 `mobile.requestClear()`，不得直接调用 `ClearMobileDisplay(true)`；取消确认不得清屏。
- [ ] 首次启动且从未打开状态面板时，快捷键先刷新 Mobile 状态，再按 `canClear` 能力打开唯一 `MobileActionConfirm`。
- [ ] 长按、快速重复、读取中、mutation 中或已有 pending 时，不重复弹窗或提交。
- [ ] 旧配置已占用 `67+160` 时保留旧 action、新 action 迁移为空绑定（此条已被第 8 节实测回修替代）。
- [ ] macOS 不新增、不显示该 action，不宣称支持。
- [ ] 状态面板鼠标按钮继续保留；补充修复不改变 Clear 的数据保留边界。

补充非目标：不新建第二个确认层、不新增清屏协议、不修改 Windows Hook 组合键算法、不统一左右 Shift，也不扩展修复快捷键录制系统的其他历史问题。

## 8. 2026-10-23 实测回修：`Shift+C` 隐藏主界面

用户使用最新验证版按左 `Shift+C` 时，主界面被隐藏，而不是只打开清屏确认层。

回修验收标准：

- [ ] 快捷键录制期间只向前端发送预览，不得在冲突检查前修改 Hook 的运行态绑定。
- [ ] 冲突录制失败后，目标 action 和被冲突 action 均保持原绑定；不能留下两个相同的非空 `ComboID`。
- [ ] 录制成功仅在松键完成并通过冲突检查后一次性提交，并发送 `shortcut-saved` 结束前端录制状态。
- [ ] Windows 旧配置缺少 `clear_mobile_display` 时，默认左 `Shift+C` 明确保留给清屏；占用该组合的旧 action 改为空绑定，避免继续执行隐藏窗口等旧动作。
- [ ] 已显式使用自定义清屏组合时继续尊重用户选择；显式空绑定且默认组合空闲时也保留。若清屏为空但旧 action 仍占用 `67+160`，视为旧版迁移残留：清空旧 action 并恢复清屏默认值。
- [ ] `Shift+C` 仍只请求唯一确认层，不直接确认清屏，不改变 Clear 的数据保留边界。
